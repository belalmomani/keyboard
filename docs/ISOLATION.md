# دراسة العزل الديناميكي (غير منفَّذة)

> **هذه دراسة وليست ميزة.** لم يُنفَّذ أي مما يلي ولم يُجرَّب على Windows حقيقي؛ الخيارات مذكورة من المعرفة العامة وتحتاج تحقق قبل الاعتماد.

## الهدف
تشغيل أمر أداة بحيث لا يتجاوز الصلاحيات الممنوحة حتى لو تحايل على الفحص الساكن.

## خيارات Windows
| الخيار | الفكرة | الملاحظات |
|---|---|---|
| Job Objects | حدود على العملية (ذاكرة، عدد العمليات، إنهاء الأبناء) | لا يقيّد الملفات/الشبكة وحده |
| Restricted Token / Low Integrity | إزالة امتيازات وخفض مستوى النزاهة | يقيّد الكتابة؛ يحتاج اختباراً مع ConPTY |
| AppContainer | عزل بقدرات (capabilities) للشبكة والملفات | الأقوى، لكنه معقّد ويكسر كثيراً من أدوات سطر الأوامر |
| تشغيل عبر WASM/WASI | الأداة نفسها تُكتب بمحرك مقيَّد | يتطلب تغيير نموذج الحزم (ليست أوامر صدفة) |

## Linux / macOS / Android (للمراحل اللاحقة)
Linux: user namespaces + seccomp + Landlock. macOS: sandbox profiles (`sandbox-exec` مُهمَل رسمياً). Android: عزل التطبيقات المدمج وصلاحيات النظام.

## التوصية المبدئية
1. Job Object + Restricted Token كخطوة أولى قابلة للقياس.
2. تقييم AppContainer بتجربة فعلية على أدوات حقيقية قبل القرار.
3. أي نموذج عزل يُوثَّق بحدوده، ولا يُسوَّق على أنه ضمان كامل.

يحتاج هذا موافقة قبل تنفيذه لأنه يغيّر طريقة تشغيل الأدوات.
